# Turso adapter: engine, transport, and transaction evidence

Research for [Map #34](https://github.com/iianjun/fin/issues/34), [ticket #37](https://github.com/iianjun/fin/issues/37). Checked 2026-11-08. This is a focused first-pass feasibility report, not implementation or hosted-service certification. No credentials, provisioning, live database calls, or local repository changes were used.

## Recommendation and tradeoff

The lowest-change initial candidate is **a remote libSQL database using `@libsql/client/http` 0.18.0 and the repository's Drizzle 0.45.4**, with explicit SDK transaction ownership and a transport that never retries or follows redirects. This preserves the existing SQLite dialect and established Drizzle integration. Its cost is serialized writes, network round trips while holding a writer lock, and a documented five-second interactive transaction limit. It assumes libSQL remains an acceptable initial engine; this report does not select that product decision. [SDK reference](https://docs.turso.tech/sdk/ts/reference), [client package](https://github.com/tursodatabase/libsql-client-ts/blob/9496c782af413f6380235c7f5d0c97b5371f49b7/packages/libsql-client/package.json), [fin dependency](https://github.com/iianjun/fin/blob/365d21e485586fded76c284e959fee27435d0431/packages/sqlite/package.json).

The newer Rust Turso engine with `@tursodatabase/serverless` is a credible second candidate for a fetch-based adapter and concurrent writes. It has different transaction APIs and batch defaults, compatibility gaps, and transport controls that require more investigation. Choosing it now increases integration and validation work; no evidence here establishes that its hosted behavior satisfies every FinStorage guarantee.

## Engine and runtime choices

libSQL is the SQLite fork; the newer Turso engine is a Rust reimplementation. `@tursodatabase/database` opens local files/in-memory databases and uses native bindings or WASM. `@tursodatabase/sync` adds local writes and explicit push/pull. Those are not remote URL/token storage substitutes. Embedded replicas and offline convergence are outside this adapter's scope. [JavaScript connection guide](https://docs.turso.tech/connect/javascript), [Turso compatibility](https://github.com/tursodatabase/turso/blob/9b71df9abfd5bef3ee3c157f7ffef57fa2ce49ba/COMPAT.md).

The libSQL package's root chooses Node/web entry points by export conditions; its dependency tree includes native `libsql`. The explicit HTTP entry point uses Hrana HTTP and avoids importing the local SQLite binding in that execution path. Runtime portability and installation without native artifacts are separate questions: bundle/import and packed-consumer tests are still required. Remote HTTP accepts libsql/HTTPS/HTTP through normalization; it rejects local-file mode and exposes custom fetch. [exports/dependencies](https://github.com/tursodatabase/libsql-client-ts/blob/9496c782af413f6380235c7f5d0c97b5371f49b7/packages/libsql-client/package.json), [HTTP implementation](https://github.com/tursodatabase/libsql-client-ts/blob/9496c782af413f6380235c7f5d0c97b5371f49b7/packages/libsql-client/src/http.ts).

Serverless has no runtime dependency entries and uses global fetch. Nevertheless its protocol implementation references `Buffer` for blobs; plain `fetch` availability alone does not prove every execution path works in a runtime without Buffer. Its main/compat configuration has no custom-fetch injection; compat explicitly rejects fetch, intMode, and sync settings. Validate chosen edge/Node runtimes rather than extrapolating a marketing compatibility claim. [serverless protocol](https://github.com/tursodatabase/turso/blob/9b71df9abfd5bef3ee3c157f7ffef57fa2ce49ba/serverless/javascript/src/protocol.ts), [compat](https://github.com/tursodatabase/turso/blob/9b71df9abfd5bef3ee3c157f7ffef57fa2ce49ba/serverless/javascript/src/compat.ts).

## Snapshots, locks, transactions, and batches

FinStorage requires one consistent context, one synchronous decision invocation, no writes for unchanged decisions, and atomic changes/revisions/the exact supplied ChangeRecord. Dependencies must remain protected through commit; automatic decision/write retries are forbidden. This is a per-invocation callback guarantee, not an end-to-end exactly-once delivery protocol. [provider contract](https://github.com/iianjun/fin/blob/365d21e485586fded76c284e959fee27435d0431/packages/provider/src/storage.ts).

For libSQL, `transaction("write")` uses BEGIN IMMEDIATE, routes writes from replicas to the primary, and excludes competing write transactions. All context queries must use that transaction handle, followed by the decision, writes and commit. Reads needing several queries can use one read transaction, accepting replica freshness separately from snapshot consistency. Independent `client.execute` calls use different logical connections and do not create a snapshot. Interactive transactions have a documented five-second timeout; bound projections and round trips matter. [transaction modes/timeouts](https://docs.turso.tech/sdk/ts/reference), [Client API](https://tursodatabase.github.io/libsql-client-ts/interfaces/Client.html).

The SDK lazily sends BEGIN alongside the first statement. `client.batch` wraps statements with conditional BEGIN/COMMIT/ROLLBACK and defaults to deferred. `executeMultiple` is not automatically atomic. Drizzle 0.45.4 `db.transaction` calls the SDK without mode arguments, ignores its behavior configuration, commits once, and attempts rollback in its catch path. Its default SDK mode is write, but explicit lifecycle ownership makes commit-phase error classification easier and prevents rollback errors from masking the original failure. [Hrana transaction source](https://github.com/tursodatabase/libsql-client-ts/blob/9496c782af413f6380235c7f5d0c97b5371f49b7/packages/libsql-client/src/hrana.ts), [Drizzle session](https://github.com/drizzle-team/drizzle-orm/blob/0.45.4/drizzle-orm/src/libsql/session.ts).

**Serverless batch differs:** plain `conn.batch(statements)` is non-atomic; successful earlier statements remain committed after a later failure. A mode such as immediate wraps the batch atomically. Compat `client.batch` supplies deferred by default. These defaults must never be conflated. [connection batch](https://github.com/tursodatabase/turso/blob/9b71df9abfd5bef3ee3c157f7ffef57fa2ce49ba/serverless/javascript/src/connection.ts), [session batch implementation](https://github.com/tursodatabase/turso/blob/9b71df9abfd5bef3ee3c157f7ffef57fa2ce49ba/serverless/javascript/src/session.ts).

Current serverless source deprecates `transaction(fn)`: unrelated concurrent statements on its shared connection can enter that transaction. `transactionAsync(tx => ...)` owns a dedicated stream; every transactional query must use its handle. Earlier connection PRAGMAs do not carry into that fresh session. This current-source distinction needs confirmation against the installed release. [dedicated transaction implementation](https://github.com/tursodatabase/turso/blob/9b71df9abfd5bef3ee3c157f7ffef57fa2ce49ba/serverless/javascript/src/connection.ts#L398).

The newer engine defaults to one writer; local MVCC plus BEGIN CONCURRENT permits optimistic concurrent writers and conflict errors. Do not copy the docs' automatic retry loop into fin. Cloud prohibits changing journal_mode and busy_timeout, so local MVCC configuration is not a hosted-service recipe. Hosted isolation, conflict codes and new-engine transaction expiry need direct verification. [concurrent writes](https://docs.turso.tech/tursodb/concurrent-writes), [Cloud limitations](https://docs.turso.tech/cloud/limitations).

## Guarded commit and uncertain outcomes

An alternative to holding the remote lock while loading context is a validated consistent snapshot followed by a single atomic write batch: compare the Vault generation/stamp, fail with a SQL constraint on mismatch, then write all state/revisions/history and advance the stamp. A zero-row conditional update alone does not abort later statements. D1 already demonstrates this design, but its multiple-primary-read stamp protocol cannot simply be transplanted onto potentially lagging replicas. Use a transaction snapshot and authoritative primary commit guard; every writer must obey the same stamp policy. [D1 implementation](https://github.com/iianjun/fin/blob/365d21e485586fded76c284e959fee27435d0431/packages/d1/src/adapter.ts), [guard tests](https://github.com/iianjun/fin/blob/365d21e485586fded76c284e959fee27435d0431/packages/d1/src/adapter.test.ts).

The inspected SDK request paths do not contain automatic SQL replay loops, but that is not a blanket guarantee about every dependency, proxy or fetch wrapper. Both inspected fetch paths omit an explicit redirect policy; standard fetch can follow redirects. libSQL custom fetch can enforce manual redirects, bounded requests and no retries. Serverless lacks equivalent per-client injection in the inspected API, making an acceptable transport boundary an unresolved gate. [Hrana HTTP transport](https://github.com/libsql/hrana-client-ts/blob/94184ccfd84731cc7c151b7a5583549961c2b20e/src/http/stream.ts), [serverless transport](https://github.com/tursodatabase/turso/blob/9b71df9abfd5bef3ee3c157f7ffef57fa2ce49ba/serverless/javascript/src/protocol.ts).

The new engine's protocol explicitly says request-level failure can discard results after committed writes. Streams use rotating batons and returned base URLs for node pinning; idle expiry rolls back open transactions. This does not prove that a lost COMMIT response means rollback. Client abort/query timeout, broken JSON, response truncation, lost acknowledgement and generic HTTP failures after commit/batch submission must conservatively become `OUTCOME_UNKNOWN` unless affirmative evidence proves non-application. Never retry COMMIT or rerun the decision. Known guard rejection/confirmed abort can be CONFLICT; malformed stored data and confirmed non-applied SQL failures map to STORAGE_FAILURE. Preserve existing FinError from the decision. [protocol §§4–5,9](https://github.com/tursodatabase/turso/blob/9b71df9abfd5bef3ee3c157f7ffef57fa2ce49ba/serverless/PROTOCOL.md), [fin errors](https://github.com/iianjun/fin/blob/365d21e485586fded76c284e959fee27435d0431/packages/provider/src/errors.ts).

## Migration reuse and verification gates

Reuse SQLite SQL/schema semantics where verified, not its synchronous better-sqlite3 connection manager. Existing assets need recursive views, expression indexes, composite foreign keys/cascades, CHECK/typeof/json_valid, rowid ordering, bound safe integers, and an identity ledger. D1 additionally requires commit guards. The Rust compatibility matrix supports many ingredients but documents partial SQLite compatibility and MVCC caveats; file compatibility does not certify query/isolation behavior. Cloud's PRAGMA restrictions also differ from local engine support. Keep migration identity specific to the exact asset and enforce foreign keys on the actual transaction/session before BEGIN. [fin schema](https://github.com/iianjun/fin/blob/365d21e485586fded76c284e959fee27435d0431/packages/sqlite/src/storage/schema.ts), [compatibility matrix](https://github.com/tursodatabase/turso/blob/9b71df9abfd5bef3ee3c157f7ffef57fa2ce49ba/COMPAT.md).

Required implementation gates:

- Run the financial contract with each chosen adapter; verify unchanged/asynchronous decisions, one decision invocation, exact history snapshots, revisions, integer boundaries and migration rollback.
- Interleave distinct remote connections: mixed context, stale dependencies, duplicate/name/category predicates, missing rows and two commits from one snapshot. Confirm losers write no history.
- Inject mid-batch constraint failure and lost acknowledgement after real commit; assert whole rollback or OUTCOME_UNKNOWN, one submission, preserved original error, and no redirects/replay.
- Test actual installed SDK/Drizzle packages in the selected runtime, detached methods, concurrent calls and session PRAGMAs.
- Separately run hosted checks for routing/replicas, lock expiry, service limits, error envelopes and migrations. Local files or local HTTP servers establish SQL/client behavior only.

No such new tests were executed in this research. Human decisions remain engine scope (libSQL first, new Turso first, or explicit separate support), initial runtime, and interactive-lock versus optimistic-guard strategy. Exact hosted guarantees and release-level newer-engine integration remain acceptance gates.
